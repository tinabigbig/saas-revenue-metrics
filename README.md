# SaaS Revenue Metrics: ARR, ACV, Billings and Upstream Change Control

A finance data case study: turning a subscription book into trustworthy ARR, ACV, billings, renewal and NRR reporting, with written treatment rules for the hard cases and a check that flags when an upstream system change would break them.

> **The data is synthetic.** It is generated by `scripts/generate_data.py` (fixed seed) to contain the edge cases that make subscription metrics hard: multi-year deals billed up front, co-termed add-ons, usage billing, credit memos, re-posted invoice rows, and an acquired company with its own schema and plan names. Totals are illustrative; the logic is the point.

## Questions this answers
1. What is ARR at each month end, and what moved it (new, acquired, expansion, contraction, churn)?
2. How should ACV treat multi-year deals and co-termed add-ons?
3. Why do billings and ARR tell different stories?
4. What are the renewal rate and net revenue retention?
5. When an upstream system adds a new product or billing frequency, what breaks, and who needs to decide?

## Results (simulated book)
| Metric | Value |
|---|---|
| ARR, Dec 2023 to Dec 2025 | $5.53M to $13.21M |
| 2025 ARR bridge | New +$4.30M, acquired +$0.36M (Apr 2025), expansion +$0.70M, contraction -$0.42M, churn -$1.33M |
| Net revenue retention, Dec 2025 | 88.4% (accounts with ARR in Dec 2024) |
| Contract-line renewal rate | 184 of 235 expiring seat lines renewed (78%), across 163 accounts (some accounts had two expiries in the window); 79.7% of expiring ARR renewed |
| Billings vs ARR, 2025 | Trailing 12-month recurring billings $12.32M vs average core ARR $11.35M: upfront and annual billing on a growing book pulls billings ahead |
| Multi-year upfront billing | 37 base contracts with TCV $5.80M and ACV $1.93M, plus 10 co-termed add-ons on the same billing (TCV $0.10M) |
| Usage, kept out of ARR | Annualized run rate about $0.53M |
| Data issues handled | 43 re-posted invoice rows removed; $50K of credit memos netted |

## How it is built
```
data/raw/*.csv         subscriptions, invoices, usage, acquired contracts (synthetic)
seeds/plan_map.csv     acquired plan -> our product code
seeds/product_catalog.csv  approved products and their revenue class (release gate)
seeds/approved_billing_frequencies.csv  approved billing frequencies (release gate)
models/staging         one clean row per line / invoice / usage month; invoices de-duplicated
models/intermediate    core + acquired lines unioned (approved recurring products only); unknown products held
                       in int_unclassified_lines; one row per line per active month end
models/marts           fct_arr_monthly, fct_arr_bridge, fct_contract_acv, fct_billings_monthly,
                       rpt_billings_vs_arr, fct_renewals, fct_nrr, fct_usage_monthly
tests/                 reconciliation and rule tests (bridge reconciles and chains, billings tie
                       to the ledger, add-ons co-term, usage never reaches ARR, no restated history)
checks/                independent pandas recomputation of ARR, billings and NRR
change_impact/         upstream change detection and LLM review prompt
```

**Verification:** `dbt build` passes 44 of 44 (16 models: 12 tables and 4 views; 25 tests; 3 seeds). `scripts/publish.py` exports the marts to `published/` only when every test passes. An independent pandas recomputation matches the marts on 7 of 7 checks (ARR at four month ends, net billings, distinct invoices, NRR). Outputs are in `docs/`.

## Upstream change control
Finance data breaks quietly when an upstream system releases something new. Two controls work together.

**1. Release gates (in dbt), enforced at publish.** Four tests must pass before anything is published:
- `release_gate_no_unclassified_products`: a product only reaches ARR or ACV if `seeds/product_catalog.csv` lists it with an approved revenue class. Unknown or unmapped products are held in `int_unclassified_lines`, never in ARR.
- `release_gate_acquired_plans_mapped`: an acquired plan with no row in `seeds/plan_map.csv` is kept (left join) and fails the gate, instead of silently dropping out.
- `release_gate_currency_is_cad`: any line not in CAD fails until an FX rule is approved.
- `release_gate_billing_frequency_approved`: a billing frequency not in `seeds/approved_billing_frequencies.csv` (for example quarterly) fails until its treatment is decided.

`usage_not_in_arr` reads the same catalog, so no product codes are hard-coded. `scripts/publish.py` runs the full build and exports the marts only if every test passes; on any failure nothing is published and the last published files stay as they were.

**2. Change detector (`change_impact/detect_changes.py`).** It compares each raw feed with a saved snapshot and reports:
- columns added or removed, and type changes (types are compared as text, integer, decimal, boolean or datetime, so different pandas versions do not raise false alarms);
- new values in rule columns (`product_code`, `billing_frequency`, `change_type`, `currency`, acquired `plan`), including a new currency such as USD;
- row counts moving more than 5%, null rates rising, numeric totals moving more than 2%;
- existing records edited or deleted (history revised), using a fingerprint of every record.

It then walks the dbt lineage from the staging model that reads the feed to every downstream model and test, and writes a review report with the decisions needed. It also writes a prompt file an analyst can give to an LLM (Claude, Copilot) to draft the treatment, SQL and test. **This step is LLM-ready, not an automated agent:** no model is called by the code, and a person reviews and decides.

**Example** (`change_impact/simulate_upstream_change.py`): the billing system adds a committed cloud-credit product (`CC_COMMIT`) and quarterly billing, starts sending two lines in USD, and quietly re-prices three historical lines; the acquired company adds an `Enterprise` plan with no mapping. The report ([docs/change_impact_example.md](docs/change_impact_example.md)) flags every one of these and lists the downstream models and tests. `scripts/publish.py` on the changed feed then stops at the gates (currency fails on 4 lines, quarterly billing on 5, the unmapped plan on 1) and publishes nothing ([docs/change_impact_dbt_run.txt](docs/change_impact_dbt_run.txt)). dbt skips everything downstream of a failed staging test, so the remaining gates run once these are resolved.

## Limits
- The data is synthetic; this is a case study, not a production system.
- Not every upstream change blocks publishing. Four rule types are gated (product, acquired plan mapping, billing frequency, currency on the core feed). Other changes, such as a new column on the acquired feed or a large swing in totals, are reported by the detector for a person to review, but do not stop the build on their own.
- The acquired feed has no currency column, so its lines are assumed to be CAD (see METRIC_DEFINITIONS.md).

## Run it
```bash
pip install -r requirements.txt
python scripts/generate_data.py
python scripts/publish.py            # build, test, publish only if everything passes
python checks/independent_check.py
# change control demo
python change_impact/detect_changes.py --snapshot
python change_impact/simulate_upstream_change.py
python change_impact/detect_changes.py --raw data/raw_changed
python scripts/publish.py changed --vars '{raw_path: data/raw_changed}' --target-path target_changed   # stops at the gates
```
